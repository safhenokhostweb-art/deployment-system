# Phase 4-A — بررسی و طراحی تجربه کاربری فارسی (فقط طراحی)

فقط Audit و طراحی. هیچ کدی نوشته نشد، هیچ Migration/Model/Database تغییر
نکرد، هیچ فایل Backend لمس نشد. این سند، مبنای تصمیم‌گیری برای فازهای
4-B به بعد است، نه خودِ پیاده‌سازی.

## ۱. خلاصه مدیریتی

Backend این سیستم (طبق ۸ فاز قبلی: MVP، Hardening، Agent Identity،
Multi-Target Domain، Execution Integration، Production Readiness) کامل،
تست‌شده (۱۱۷ تست سبز) و پایدار است. مشکل، منطق نیست — **لایه‌ی نمایش**
است: پنل فعلی مستقیماً روی مدل داده‌ی داخلی سوار شده (project_key،
agent_token، JSON پایپ‌لاین خام، badge‌های انگلیسی)، یعنی دقیقاً برای
کسی طراحی شده که همان کسی است که این سیستم را ساخته — نه برای کاربر
نهایی‌ای که فقط می‌خواهد «سرورش را وصل کند و پروژه‌اش را دیپلوی کند».

تصمیم معماری محوری این سند: **تفکیک صریح بین «شناسه‌ی Backend» و «لایه‌ی
نمایش»**. هر جدول، هر Enum، هر route name همان‌طور که هست می‌ماند؛ آنچه
تغییر می‌کند فقط چیزی است که کاربر روی صفحه می‌بیند. این تفکیک، خودِ اصل
راهنمای کل فازهای 4-B به بعد است، نه یک جزئیات پیاده‌سازی.

یافته‌ی مهم دیگر (بخش ۱۲): بخشی از Wizardهای درخواستی (اتصال واقعی
GitHub، انتخاب Deployment Target از UI، نصب خودکار Agent) در حال حاضر
به تغییرات Backend نیاز دارند که این فاز صریحاً اجازه نداده — این
سند این تناقض را پنهان نمی‌کند، بلکه آن را به‌عنوان یک Gap مستند‌شده
برای تصمیم آگاهانه در فازهای بعدی ثبت می‌کند.

## ۲. Current UX Audit

بررسی مستقیم فایل‌های Blade و route های موجود (نه حدس):

### مشکلات ساختاری سراسری
- کل پنل LTR و انگلیسی است؛ هیچ زیرساخت i18n وجود ندارد.
- ناوبری فعلی (`layouts/app.blade.php`): «Dashboard / Projects /
  Servers / Agents» — چهار کلمه که «Agent» در میان آن‌ها برای کاربر
  غیرفنی بی‌معنی‌ترین است (کاربر نمی‌داند Agent با Server چه فرقی دارد).
- پیام‌های خطا مستقیماً از `abort()` بک‌اند به کاربر می‌رسند، بدون هیچ
  لایه‌ی ترجمه/انسانی‌سازی. نمونه‌ی واقعی از کد فعلی
  (`DeploymentDispatcher::createMultiTarget`):
  `"Project 'X' has an Environment configured but no active deployment targets."`
  — این جمله برای یک کاربر غیرفنی، هم گیج‌کننده و هم دلهره‌آور است.
- Empty State ها حداقلی‌اند (فقط متن «No servers registered yet.»)، بدون
  آیکون، بدون توضیح، بدون دکمه‌ی اقدام بعدی.
- تأیید عملیات خطرناک (Rotate، Disable، Reject) با `onsubmit="return confirm(...)"` یعنی دیالوگ native مرورگر — نه قابل استایل‌دهی، نه
  به‌خوبی قابل ترجمه در همه مرورگرها.

### صفحه به صفحه

| صفحه | مشکل مشخص |
|---|---|
| `servers/create` | متن راهنما صراحتاً می‌گوید «... paste the credentials shown next into its config.php» — فرض می‌کند کاربر با فایل‌سیستم سرور و مفهوم config.php آشناست. |
| `servers/show` | نمایش خام `agent_token`، `signing_secret`، `public_id` (UUID) با برچسب‌های فنی؛ فرض دانش HMAC/config.php برای «استفاده» از این مقادیر. |
| `projects/create` | فیلد **project_key** با توضیح «باید با کلیدی در نقشه‌ی `projects` در config.php سرور مطابقت داشته باشد» — دقیقاً همان جمله‌ای که هدف این فاز می‌گوید نباید به کاربر نهایی برسد. فیلد **Pipeline** یک `<textarea>` خام برای نوشتن دستی JSON با placeholder syntax (`{branch}`, `{commit}`) — این چیزی است که پروژه صراحتاً خواسته کاربر هرگز نبیند. |
| `agents/pending` | نمایش `public_id`، `os`، `architecture`، و JSON خام `capabilities` — اصطلاحات کاملاً فنی برای تصمیم «تأیید/رد» که کاربر نهایی اصلاً نباید در معرض آن باشد. |
| `deployments/show` | badge‌های وضعیت انگلیسی (`queued`/`running`/`succeeded`/`failed`/`partial_success`)؛ اصطلاحات «Trigger»، «Rollback of»؛ commit hash کامل/خلاصه بدون برچسب ساده. |
| `deployment-tasks/show` | «Attempt N»، خروجی خام Pipeline (stdout/stderr) بدون هیچ خلاصه‌سازی بصری برای کاربر غیرفنی. |
| Dashboard | دو جدول جدا (Servers، Recent deployments) بدون KPI/شمارش کلی، بدون فید ترکیبی رویدادها. |

### نتیجه‌ی صریح Task 1
پنل فعلی **کاملاً برای Developer طراحی شده** — همان‌طور که خودِ درخواست
این فاز هم تشخیص داده. این ارزیابی، نه اغراق است نه دست‌کم‌گیری؛ مستقیماً
از خواندن کد فعلی گرفته شده.

## ۳. Persian Localization Strategy

### ساختار ترجمه
یک منبع واحد ترجمه در قالب فایل‌های زبان Laravel
(`lang/fa/*.php` — مثلاً `lang/fa/deployment.php`, `lang/fa/agent.php`)
که Viewها از آن می‌خوانند. **Backend هرگز این فایل‌ها را نمی‌خواند** —
جهت وابستگی فقط یک‌طرفه (View → Lang file) است، دقیقاً مثل این‌که
امروز `layouts/app.blade.php` رشته‌های انگلیسی هاردکد دارد، فقط این‌بار
از یک فایل مرکزی می‌آیند.

### قاعده‌ی بنیادین (تکرار عمدی، چون مهم‌ترین قانون این فاز است)
> نام‌های Backend (نام جدول، نام Model، نام column، نام route، مقدار
> دقیق Enum در دیتابیس) **هرگز تغییر نمی‌کنند**. آنچه در این بخش می‌آید
> یک "Dictionary" برای لایه‌ی نمایش است، نه یک دستور تغییر کد.

مثال دقیق از خود درخواست: در دیتابیس همچنان `Deployment` می‌ماند؛ روی
صفحه «استقرار» نمایش داده می‌شود.

### واژه‌نامه‌ی پیشنهادی

| اصطلاح Backend (بدون تغییر) | نمایش فارسی |
|---|---|
| Dashboard | داشبورد |

(«مراحل اجرا»، «بازگشت به نسخه‌ی قبل») باید پیش از نهایی‌شدن، با چند
کاربر واقعی فارسی‌زبان تست شود، نه صرفاً حدس زده شود (ریسک، بخش ۱۲).

## ۴. RTL Design

- **Layout پایه**: `dir="rtl"` روی `<html>`، فونت فارسی self-hosted
  (نه CDN — طبق قانون «بدون Dependency غیرضروری» کل پروژه؛ Google Fonts
  هم یک وابستگی شبکه‌ای بیرونی است). فلش‌ها/آیکون‌های جهت‌دار (مثلاً
  «بعدی» در Wizard) باید در RTL معکوس شوند.
- **Sidebar به‌جای nav افقی فعلی**: با رشد تعداد بخش‌ها (داشبورد، پروژه‌ها،
  سرورها، کارگزارها، استقرارها، و به‌زودی شاید بررسی سلامت/تنظیمات)، یک
  ستون کناری راست (در RTL منطقی سمت راست) خواناتر از nav افقی است.
- **Header**: نام کاربر، دکمه خروج؛ در نبود سیستم نقش (بخش ۹) فعلاً چیز
  بیشتری لازم نیست.
- **Tables**: جهت کلی راست‌به‌چپ، اما هر عدد/کد/hash/تاریخ‌میلادی باید
  داخل یک عنصر با `dir="ltr"` مجزا قرار گیرد — وگرنه commit hash یا
  اعداد در RTL به‌هم‌ریخته نمایش داده می‌شوند (این یک قانون Component
  است، نه استثنا به استثنا).
- **Status badges**: رنگ + آیکون، نه فقط متن — تا حتی بدون خواندن دقیق،
  وضعیت (سبز=موفق، قرمز=ناموفق، آبی=در حال اجرا، زرد=در انتظار) در نگاه
  اول قابل تشخیص باشد.
- **Forms**: label راست‌چین؛ خودِ ورودی بر اساس محتوایش جهت می‌گیرد
  (فارسی راست‌چین، URL/کد انگلیسی چپ‌چین).

### Component های لازم (Inventory)
`Badge` (وضعیت)، `Card`، `Table` (با ستون عددی/کد ایمن در برابر RTL)،
`Form Field` (label + input + راهنما + خطا در یک بسته)، `Wizard Stepper`
(نشانگر مرحله‌ی جاری از N مرحله)، `Confirm Modal` (جایگزین
`window.confirm` فعلی، قابل استایل و ترجمه)، `Empty State` (آیکون +
پیام + دکمه‌ی اقدام)، `Alert/Toast` (جایگزین `session('status')` ساده‌ی
فعلی)، `Sidebar Nav Item`، `Breadcrumb`.

### کدام‌ها Shared هستند
`Badge`، `Card`، `Table`، `Empty State`، `Alert`، `Confirm Modal`، و
`Wizard Stepper` در هر بخش (سرورها/پروژه‌ها/استقرارها/کارگزارها) تکرار
می‌شوند — باید یک‌بار به‌صورت Blade Component (`<x-badge status="..."/>`
و مشابه) ساخته شوند، نه در هر View کپی-پیست (دقیقاً همان الگویی که امروز
در `layouts/app.blade.php` با کلاس‌های `.badge-*` به‌صورت CSS خام وجود
دارد و باید به Component واقعی ارتقا یابد).

## ۵. Dashboard Design

طبق Task 4، چیدمان پیشنهادی:

**ردیف اول — چهار گروه KPI Card:**
- سرورها: کل / آنلاین / آفلاین
- کارگزارها: فعال / نیازمند تأیید (این یکی با یک Badge عددی جلب‌توجه،
  مشابه نوتیفیکیشن — چون «نیازمند تأیید» یک اقدام معلق از سمت ادمین
  می‌خواهد)
- پروژه‌ها: تعداد کل، آخرین Deploy (زمان نسبی فارسی: «۲ ساعت پیش»)
- استقرارها: موفق / ناموفق / در حال اجرا

هر KPI باید قابل کلیک باشد و به لیست فیلترشده‌ی مربوطه برود (کلیک روی
«ناموفق» باید مستقیم استقرارهای ناموفق اخیر را نشان دهد) — این یک قانون
تعامل است، نه فقط نمایش عدد بی‌کنش.

**ردیف دوم — فید ترکیبی رویدادها:** به‌جای دو جدول مجزا (Servers,
Recent deployments) که امروز وجود دارد، یک فید واحد از رویدادهای اخیر
(استقرار جدید، کارگزار جدید نیازمند تأیید، نتیجه‌ی بررسی سلامت) —
دقیق‌تر و کم‌تکرارتر از پیمایش دو جدول جدا.

**Empty State سطح داشبورد:** وقتی سیستم تازه نصب شده (هیچ سرور/پروژه‌ای
نیست)، به‌جای جدول خالی، یک پیام راهنما با دکمه‌ی مستقیم: «هنوز سروری
اضافه نکرده‌اید — برای شروع، سرور اول خود را اضافه کنید [دکمه]».

## ۶. Server Wizard

پنج مرحله طبق Task 5، با تصمیم‌های دقیق هر مرحله:

**مرحله ۱ — نام سرور:** فقط یک فیلد متنی + یک جمله راهنما (بدون اشاره
به config.php). این بخش دقیقاً معادل امروزیِ `servers.create` است، فقط
بدون متن فنی.

**مرحله ۲ — نوع سرور (VPS / cPanel / Shared Hosting):** این انتخاب
**صرفاً لایه‌ی نمایش است** — امروز `Server` در Backend هیچ فرقی بین این
سه نمی‌گذارد. بر اساس این انتخاب، فقط متنِ راهنمای نصب در مرحله‌ی ۳ فرق
می‌کند (مثلاً VPS → راهنمای systemd؛ cPanel → راهنمای Cron Job). اگر در
پیاده‌سازی واقعی لازم شد این انتخاب ذخیره هم بشود، یک ستون اختیاری
(migration جداگانه، نه این فاز) کافی است — اما حتی بدون ذخیره‌سازی هم
این مرحله در Wizard قابل اجراست (فقط تعیین می‌کند کدام متن نشان داده
شود).

**مرحله ۳ — نصب کارگزار:** اینجا مهم‌ترین Gap این سند است (بخش ۱۲):
طراحی ایده‌آل یک **Installer یک‌خطی** است (کاربر یک دستور copy-paste
می‌کند که PHP را چک می‌کند، فایل agent را دانلود می‌کند، و config.php
را با token/secret از پیش تولیدشده خودش می‌سازد) — این نیازمند یک
اسکریپت نصب‌کننده‌ی جدید در `agent/` است که **امروز وجود ندارد** و
ساختنش کدنویسی Backend/Agent می‌خواهد، نه صرفاً UI. برای این فاز، فقط
طراحی مفهومی ثبت می‌شود؛ ساخت واقعی آن یک Task مشخص در Phase 4-D است.

**مرحله ۴ — تأیید اتصال:** یک صفحه‌ی در حال انتظار (Polling خودکار،
هر چند ثانیه) تا لحظه‌ای که کارگزار موفق به Register/Heartbeat شود.
**تصمیم UX مهمی که باید همین‌جا صریح گرفته شود**: آیا در همین Wizard،
تأیید کارگزار خودکار انجام شود (بدون نیاز به رفتن به صف
Pending Approval جداگانه)؟ **پیشنهاد این سند: بله** — چون کسی که این
Wizard را اجرا می‌کند خودش همان ادمینی است که سرور را نصب کرده، تأیید
دستی اضافه در همین لحظه فقط اصطکاک بی‌فایده ایجاد می‌کند. این باید
به‌عنوان یک تصمیم رسمی در پیاده‌سازی Phase 4-D اجرا شود، نه چیزی که در
حین کدنویسی به‌صورت ضمنی تصمیم‌گیری شود.

**مرحله ۵ — آماده استفاده:** پیام موفقیت + دکمه‌ی مستقیم «ایجاد پروژه»
که کاربر را به Project Wizard می‌برد.

## ۷. Project Wizard

شش مرحله طبق Task 6:

**مرحله ۱ — اطلاعات پروژه:** نام + نوع پروژه (Laravel / Node.js /
WordPress / Custom). این انتخاب یک Template پیش‌فرض Pipeline را
فعال می‌کند (امروز فقط تمپلیت Laravel در
`ProjectController::DEFAULT_LARAVEL_PIPELINE` وجود دارد؛ معادل
Node.js/WordPress باید ساخته شود — کار Phase 4-E، نه این سند).

**مرحله ۲ و ۳ — اتصال GitHub و انتخاب Repository:** **مهم‌ترین Gap این
سند.** طراحی ایده‌آل («انتخاب از لیست Repository های GitHub») نیازمند
GitHub App/OAuth است که **امروز در Backend اصلاً وجود ندارد** (فقط
Webhook URL/Secret دستی). ساختن آن، یک تصمیم معماری Backend واقعی است
که این فاز صراحتاً اجازه نداده. **راه‌حل موقت پیشنهادی برای Phase 4 (بدون
تغییر Backend)**: کاربر همچنان `owner/repo` را دستی تایپ می‌کند (دقیقاً
مثل امروز)، اما با یک فرم راهنمای گام‌به‌گام («این آدرس را از صفحه‌ی
مخزن خود در GitHub کپی کنید»)؛ و بعد از ذخیره، دستورالعمل مصور «این URL
و این Secret را در تنظیمات Webhook مخزن‌تان وارد کنید» (بهبود UI روی
همان چیزی که امروز هست، نه قابلیت جدید). تصمیم واقعی (ساخت GitHub App)
باید رسماً به فازی بعد از Phase 4 موکول شود (بخش ۱۱).

**مرحله ۴ — انتخاب Branch:** فیلد متنی ساده (پیش‌فرض `main`) — انتخاب
از لیست واقعی Branchهای GitHub هم به همان GitHub API وابسته است که در
مرحله‌ی ۲/۳ نیست؛ فعلاً متنی می‌ماند.

**مرحله ۵ — انتخاب مقصد استقرار (Deployment Target):** این مستقیماً
روی مفهوم Backend موجود `DeploymentTarget` (ساخته‌شده در Phase 3-C)
سوار می‌شود — اما **امروز هیچ رابط کاربری برای ساختن `Environment`/
`DeploymentTarget` وجود ندارد** (فقط از طریق کد/Tinker قابل ساخت است).
این هم یک Gap صریح است: قبل از این‌که این مرحله از Wizard واقعاً کار
کند، باید یک CRUD ساده برای Environment/Target ساخته شود (Controller و
Route جدید — کار Backend، هرچند کوچک، نه صرف UI). در نبود آن، این مرحله
در نسخه‌ی اول Wizard می‌تواند به همان مدل امروزی (یک سرور واحد) محدود
بماند و «چند سروری» به‌عنوان یک گزینه‌ی پیشرفته‌ی بعدی اضافه شود.

**مرحله ۶ — انتخاب Pipeline:** بر اساس نوع پروژه (مرحله ۱) از پیش
انتخاب می‌شود؛ کاربر می‌تواند مرور/ویرایش جزئی کند، اما **نه با
ویرایش JSON خام**. پیشنهاد: یک «سازنده‌ی مرحله» (دکمه‌ی «افزودن مرحله» +
فیلد نام + یک دستور از پیش‌تعریف‌شده یا آزاد) که در پس‌زمینه همان JSON
را می‌سازد — کاربر هرگز مستقیماً `{branch}`/`{commit}` را نمی‌بیند مگر
حالت «Custom» را انتخاب کرده و حتی آن‌جا هم قالب راهنما دارد.

## ۸. Deployment Experience

طبق Task 7، صفحه‌ی Deployment Detail:

- **پروژه، محیط، سرور، کارگزار**: نام‌های خوانا (نه ID خام) — این
  بخش‌هایش امروز تا حدی وجود دارد (Phase 3-C.2/3-D)، فقط برچسب‌ها باید
  فارسی شوند.
- **مراحل اجرا**: هر Step با آیکون وضعیت (✓ / ✗ / در حال اجرا) در یک
  Timeline عمودی، نه فقط لیست متنی.
- **Log**: پیش‌فرض جمع‌شده (Collapsed)؛ دکمه‌ی «نمایش جزئیات فنی» برای
  باز کردن خروجی خام — کاربر عادی فقط سبز/قرمز هر مرحله را می‌بیند، نه
  stdout مگر بخواهد.
- **نتیجه**: یک بنر رنگی بزرگ بالای صفحه: «استقرار با موفقیت انجام شد» /
  «استقرار ناموفق بود — [خلاصه‌ی دلیل، نه پیام خام Exception]» / «در حال
  اجرا...».
- **وضعیت‌ها**: طبق واژه‌نامه‌ی بخش ۳.
- **چندهدفه (Multi-target)**: یک نمای Grid — هر Target یک کارت مجزا، به‌علاوه یک نوار پیشرفت «۲ از ۳ سرور تکمیل شد».

## ۹. Security UX

طبق Task 8 — قوانین موجود که باید حفظ شوند (از Phase 1.5/3-B/3-D):
**نمایش یک‌بار** (agent_token، signing_secret، registration token،
webhook secret همه همین الگو را دارند)، **Mask** (webhook secret از
Phase 3-D)، **Rotate** (هر دو سرور و پروژه از قبل این قابلیت را دارند).
این‌ها تغییر نمی‌کنند — فقط باید در پنل فارسی با متن مناسب («این مقدار
فقط یک‌بار نمایش داده می‌شود — همین الان آن را کپی کنید») دوباره ساخته
شوند.

**یافته‌ی مهم‌تر:** کاربر نهایی غیرفنی اصلاً نباید این صفحات را ببیند.
امروز هیچ تفاوت نقشی وجود ندارد — هر کاربر واردشده معادل «ادمین کامل»
است. برای یک محصول واقعی تجاری، حداقل دو سطح دسترسی لازم است: «مدیر
سیستم» (می‌بیند token/secret/می‌تواند سرور ثبت کند) و «کاربر پروژه» (فقط
Deploy/مشاهده‌ی وضعیت، بدون هیچ صفحه‌ی Secret). **این خودش یک تغییر
Backend واقعی است (نقش/Permission)** که این فاز اجازه‌ی اجرایش را نداده
— پس فقط به‌عنوان پیش‌نیاز معماری برای تجاری‌سازی واقعی در بخش ۱۱/۱۲ ثبت
می‌شود، نه چیزی که در Phase 4-B..F گنجانده شود.

در نبود سیستم نقش، حداقل اقدام ممکن در همین محدوده: صفحات حاوی Secret
(نمایش Server، نمایش/تأیید Agent، چرخش Secret پروژه) در ناوبری اصلی
پررنگ نباشند — زیر یک بخش «تنظیمات پیشرفته» مخفی شوند، نه در مسیر
روزمره‌ی کاربر.

## ۱۰. Commercial Readiness

ارزیابی صادقانه طبق معیارهای Task 9:

| معیار | وضعیت فعلی |
|---|---|
| ساده بودن | خیر — همین سند دلیلش است |
| عدم نیاز به دانش DevOps | خیر — فیلدهای project_key، JSON Pipeline خام، اشاره‌ی مستقیم به config.php دقیقاً همان چیزی هستند که باید حذف شوند |
| Error Message مناسب | خیر — پیام‌های `abort()` انگلیسی/فنی مستقیم به کاربر می‌رسند (نمونه‌ی دقیق در بخش ۲) |

**نتیجه‌ی صریح**: پنل فعلی برای ارائه به مشتری غیرفنی آماده نیست. اما
خبر خوب این است که این ریسک **کاملاً در لایه‌ی نمایش است، نه در منطق یا
امنیت زیرین** — Backend با ۱۱۷ تست پایدار است و این فاز آن را دست‌نخورده
نگه داشته. یعنی بازسازی UI (فازهای 4-B به بعد) ریسک کمی برای صحت داده یا
امنیت دارد؛ کار اصلی، طراحی و پیاده‌سازی رابط است، نه اصلاح منطق.

## ۱۲. Risks

- **بزرگ‌ترین ریسک**: بخشی از Wizardهای درخواستی (اتصال واقعی GitHub با
  انتخاب از لیست، انتخاب Deployment Target از UI، نصب خودکار کارگزار)
  در عمل به تغییرات Backend نیاز دارند که این فاز صریحاً ممنوع کرده. این
  تناقض در بخش‌های ۶/۷/۱۱ به‌جای پنهان‌شدن، صریحاً مستند شده — تصمیم
  آگاهانه («این Gapها را در Phase 4-D/4-E به‌عنوان Backend Task کوچک
  می‌پذیریم» یا «Wizard را به قابلیت‌های امروزی محدود می‌کنیم») باید
  پیش از شروع کدنویسی 4-B گرفته شود، نه حین کار.
- **ریسک ترجمه**: «Pipeline» و «Rollback» معادل فارسی جاافتاده‌ی
  یکسانی ندارند؛ پیشنهادهای بخش ۳ باید با کاربران واقعی فارسی‌زبان تست
  شوند، نه فقط بر اساس حدس این سند نهایی شوند.
- **ریسک فونت/Dependency**: فونت فارسی باید self-hosted باشد، نه از
  CDN بیرونی (Google Fonts و مشابه) — طبق قانون «بدون Dependency
  غیرضروری» که در تمام فازهای قبلی این پروژه رعایت شده.
- **ریسک دوزبانگی پنهان**: چون Backend انگلیسی می‌ماند، خروجی خام
  Pipeline و برخی پیام‌های Agent همچنان انگلیسی خواهند بود. برای کاربر
  کاملاً غیرفنی، حتی یک خط لاگ انگلیسی می‌تواند نگران‌کننده باشد — باید
  صریحاً مشخص شود چه بخش‌هایی اصلاً نباید به این کاربر نمایش داده شوند
  (نه فقط ترجمه شوند)، دقیقاً همان اصل «جمع‌شده به‌صورت پیش‌فرض» در
  بخش ۸.
- **ریسک گسترش دامنه (Scope Creep)**: با توجه به Gapهای کشف‌شده، وسوسه‌ی
  گسترش Phase 4 به تغییرات Backend بالاست. توصیه‌ی این سند: مرزهای
  فازبندی بخش ۱۱ به‌عنوان مرجع تصمیم استفاده شود، نه چیزی که در حین
  پیاده‌سازی بازتعریف شود.
